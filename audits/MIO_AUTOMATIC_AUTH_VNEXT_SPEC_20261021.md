# MIO 自動本人認証 vNext — 実装仕様・安全ゲート (2026-10-21)

状態: **設計確定候補・本番未適用**。既存の公開URL、MIO-ID、皆勤、ガチャ、当選、端末切替履歴は保持。

## 目的
管理者への承認問い合わせを減らす。登録直後のフォーム利用・ギャラリー閲覧は本人確認とは分離し、他人のMIO-IDへの自動紐付けは防ぐ。

## IDと資格情報
- 主キー: immutable MIO-ID。表示名/ColorSing名は同一性証明にしない。
- Web登録ID: MIO-IDに最大5件の**アクティブ**なブラウザ登録。上限到達時は古い登録を無条件削除せず、認証済みセッションで利用者が解除する。
- IP: 直近5件までのIP観測履歴（短期TTL・最小限の保持・アクセス制限）。共有/変動するため**承認の独立要因として数えない**。
- User-Agent/端末特徴: 不審な変化の検知のみ。フィンガープリントによる無断追跡はしない。
- パスキー(WebAuthn): credential ID, public key, signCount, transports, backup flags等の検証可能な公開情報をサーバーに保存。秘密鍵・顔画像・指紋は収集しない。Androidの画面ロック/指紋、iPhone Face ID等をOS側で利用。
- 登録済みセッション: 高エントロピーな失効可能トークンのハッシュのみ保存。サーバーで期限/端末/失効を検証。
- 端末追加コード: 短寿命・一回限り・試行回数制限。既に強く認証された端末から承認。

## 認証状態機械
1. guest -> registered_limited: Web登録後、許可されたフォーム・ギャラリー閲覧のみ。**API側でも**権限を分離。
2. registered_limited -> authenticated: (A) 既存パスキーのチャレンジ署名をサーバー検証、または (B) 有効な既存セッション + 明示的な再認証、または (C) 既存認証端末での短寿命ペアリング承認。
3. authenticated -> linked: MIO-IDへの対応関係を検証し、トランザクション/ロックの下で端末登録。重複名前やIP一致だけで昇格しない。
4. recovery_required: 強い資格情報がない場合は段階的な復旧を案内。最終手段のみ管理者本人確認。

## 自動承認の原則
- 「3項目一致」は**補助リスク判定**に限る。名前・MIO-ID・IP・User-Agentなど相関した情報を3つ数えても承認しない。
- 初回本人確認のブートストラップが必要。既存のGAS「承認済み」を無条件で本人確認済みと見なしてパスキー発行しない。
- 同じMIO-IDの既存端末を勝手に失効させない。切替操作は本人の明示的な選択・強い認証・監査ログを要する。
- パスキー未対応端末には、認証済み端末からの追加または回復手段を用意する。

## 実装順序
P0: 既存GitHub/Vercelの認可ガードを読取り監査。フォーム・ギャラリー閲覧と参加者データ書込み/皆勤/ガチャ権限を分離。公開動作を変えない。
P1: 非本番ブランチにサーバー側スキーマ/認証状態/ログ/レート制限とモックテストを追加。
P2: WebAuthn登録・認証・複数端末追加・失効・回復の統合テスト。
P3: GAS4ファイルと公開デプロイv12のソース差分、実トリガー、データマッピングを読み取り確認。
P4: バックアップ、ロールバック、テストアカウントで実動作検証してから明示的な公開判断。

## 必須テスト
- 同名別人/同IP別人/漏れたMIO-ID -> 自動リンク拒否
- 正しいパスキーでIP変更 -> 自動ログイン可
- 5ブラウザ上限/古い端末/同時登録競合 -> データ消失なし
- ガチャ/皆勤/当選/履歴の権限昇格なし
- フォーム・ギャラリー閲覧のみの登録直後利用は維持
- パスキー取消・セッション失効・リプレイ・チャレンジ期限切れ・CSRF -> 拒否
- GAS setup()等は実行しない。公開URL/既存デプロイは変更しない。
