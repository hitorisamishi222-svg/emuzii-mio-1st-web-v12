# 次期統合版：TEST専用データと認証の設計

## 状態
- `next_test` スキーマのSQLは**コードとして準備しただけ**。どのDBにも適用していない。
- Supabaseやその他のDB契約・課金を作成していない。機能利用前に利用先と運用予算の最終承認を受ける。
- 既存Google Sheetsの本番データとは分離する。本番のGAS、`APPS_SCRIPT_SECRET`、参加者情報を複製しない。

## サーバーの権限判定
1. HTTP CookieのHMACを検証。利用者がブラウザから送信したロールや名前は信用しない。
2. TEST専用の本人確認サービスがMIO-ID相当のテスト識別子、有効な端末・ブラウザの状態、運営承認を返す。
3. `community_write` を別の認可として検証。メンシプ加入/ガチャ権利はコミュニティ投稿権限に転用しない。
4. 投稿時にTEST側 `community_posts` 停止スイッチがONか検査。DBの初期値は停止（false）である。
5. 5秒投稿間隔、1分5件、本文300文字、CSRF/Origin/Fetch Metadata、永続レート制限、冪等性を検証。
6. 投稿は `pending` へ保存。管理者認証を持つモデレーターによる承認後のみ一般公開。
7. 公開APIのJSONには許可された公開ニックネーム、本文、日時等だけ含める。ログインID、MIO-ID、内部DBキー、ファイル格納キーは出さない。
8. 管理者の承認・却下・停止操作は監査ログに記録。システム全停止と投稿のみ停止を分離。

## 既存v1.9.1認証から引き継ぐ際の注意
- 公開中のログインIDは8桁の16進文字列を使うコードがある。本人確認の唯一の鍵としてコミュニティ管理操作を解放しない。
- ログインID発行処理に明示的な全件重複検査が見えない。登録・復旧要求にはサーバー側の総量制限と失敗回数制限が必要。
- v1.9.1の同名+ログインID復旧は新たなWeb登録を作る。**別ブラウザの同一所有者である証明と、旧セッションの失効を混同しない。**
- 正式なコミュニティ本人認証には、十分長い一回限りの復旧トークンや運営確認、既存MIO-IDとの一致・監査を組み合わせる。
- サーバーとTEST DBの実接続、データの隔離、負荷/認証/E2Eテストは未実施。
