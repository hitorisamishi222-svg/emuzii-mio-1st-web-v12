# みおシステム：現場個別承認を最短で安全に解放する手順（2026-11-05）

## 運用目的と最重要条件

お客様が来場してから管理者が本人・メンシプ・既存MIO-ID・元の登録端末・残回数を確認し、その人だけ承認／必要に応じて回数付与する。**全体大型アップデートの全テスト合格や、架空顧客を使った本番抽選テストを要求しない。**

管理者はColorSing名から既存参加者候補を探せる。**名前一致は本人認証にならない。** 8桁のログインIDをお客様に暗記させたり、新しいMIO-IDを安易に発行したりしない。既存のガチャ権利・当選履歴・皆勤データ・本番URLを維持する。

## 現状：本番復旧を阻む事実

1. 本番管理画面の `POST /api/gacha-admin-ops` が `read invalid identity` で失敗。管理者認証は通っているが、稼働GASが `webAdminOpsRead` 管理命令に対応していない可能性が高い。
2. Driveに保存された10/11の `Code.gs` バックアップとv1.9.1参照原本は、共有秘密鍵確認後に参加者IDチェックへ進み、管理Opsへの特別ルートを含まない。ただし**現行のApps Scriptソース／デプロイと同じ保証はない**。
3. GitHubに保存された統合候補 `GAS_Code_FULL_WEB_OPS_20261030.gs` と単独モジュール `GAS_WebAdminOps_20261030.gs` は**19関数が完全重複**。両方を貼り付けたり、実稼働 `Code.gs` を全文置換したりしてはいけない。
4. 管理操作候補は初回書き込み時に `emuzii_Web管理操作履歴` タブを作成し、付与時に `emuzii_ガチャ付与履歴` J列の `Web操作ID` を使用する。以前の実シート読み取りでは監査タブ・J列見出しは未設置だった。**ユーザー権利を変えないシート構造確認・必要な準備が先。**
5. 現場用Web管理PR #79のAPIは `MIO_GACHA_ONSITE_RELEASE` が未設定の限り書き込み停止。管理機能の重点テストは77/77合格（2026-11-05）が、これは本番のGAS読み取り成功を意味しない。
6. 2026-11-05に稼働スプレッドシートの**見出しだけ**を再照合。`emuzii_Web登録` A:U（21列）、`emuzii_参加者` A:J（10列）、`emuzii_ガチャ` A:Q（17列）、`emuzii_ガチャ付与履歴` A:I（9列）、`emuzii_新規簡易登録` A:F（6列）、`emuzii_当選履歴` A:O（15列）は候補GASの参照位置と一致。`emuzii_Web管理操作履歴` は未作成。既存データ行は変更していない。
7. 本番Vercelの一次URLは引き続き `main` commit `84c623de9961a801f30b978bda8b8bea7a0daf4e` のREADYデプロイ。開発PR #79はDraftかつ本番未反映。
8. 現在のライブGASの全ファイルを確認する際は、候補の19関数だけでなく、`json_`、`safeText_`、`webIntegrityOk_`、`ensureWebDerivedRow_` の既存ヘルパー有無も点検。欠損している場合は変更停止。

## 2026-11-06 既存GAS実機確認後の最短復旧判断

- ユーザーが開いた `emuzii 翠央1周年 Web連携 v1.2` の**現行エディタ** `Code.gs` 全文には、`doPost` の `webAdminOps(Read|Approve|Grant|Review|Create|Intake)` 分岐と、`mioAdminOps_` から `mioAdminOpsIntake_` の19関数が**すでに存在**した。
- **ただしエディタ上部には「変更が保存されていません」** と出ており、これが本番公開中の**バージョン15（2026-10-30 13:01）**と同一のソースかは未確認。実際のVercelログでは管理読み取りが `invalid identity` に到達している（2026-11-05 18:56〜19:00 JST）。 
- Vercel本番 `APPS_SCRIPT_URL` のWebアプリデプロイIDとユーザーのデプロイ管理画面のIDが一致することは別途確認済み。**接続先URLを変える必要はない。**
- 今必要な唯一の未取得資料は**既存Apps Script「プロジェクトの履歴」内の公開版15の `Code.gs`**。現行エディタの再コピー・同じ関数検索・スマホ実機での再試験・古いバックアップ再送は不要。バージョン15の全コードと現行エディタとの差を照合する。
- もし公開版15に管理ルーティングがなく、既存の全関数もないと確認できた場合に限って、適用用の**一行の `doPost` 分岐 + 欠損している管理関数のみ**を、稼働GASのバックアップと変更前ハッシュを取得後に検討する。全文置換を絶対にしない。
- もし公開版15に管理ルーティングがあるなら、**コードは追加しない**。Vercelが見ている実際の実行デプロイ/秘密鍵/分岐条件を読み取り専用で調べる。
- **未保存状態で保存・実行・更新は行わない**。実際に本番で管理操作を動かすには、現行プロジェクトに安全なコードを保存し**同じWebアプリデプロイを新しいバージョンへ更新する工程**が必要だが、その承認判断は上記差分確定後とする。

## 完了ゲート A：稼働中GASの読み取り確認（本番書き込み禁止）

既存の管理スプレッドシート → 拡張機能 → Apps Scriptで、紐付いた**既存プロジェクト**を開く。以下だけを確認・記録する。

- Apps Scriptの**既存プロジェクトID、ファイル名一覧、各ファイルのバックアップと変更前ハッシュ**。秘密鍵、参加者ID、個人情報、ソース全量を公開Issueに貼らない。
- 「デプロイを管理」から**現行のWebアプリデプロイID・稼働バージョン・実行ユーザー・アクセス範囲**を確認。新規デプロイ作成ではない。
- `doPost(e)` が何個あるか、`BRIDGE_SECRET` 認証と `LockService` の順番、`webGateRead/Set`、`webAdminOpsRead/Approve/Grant/Review/Create/Intake` の分岐と19関数の有無を確認。
- 本番ソースに管理分岐が**すでにある**ならコード追加は不要。未対応なら、既存の `doPost` の**秘密鍵確認後・参加者ID検証前・同じScriptLock内**だけを検討。19関数の重複を避け、既存のチェックイン／抽選・復旧コードには触れない。
- 10/11のバックアップ、10/30の統合候補だけを稼働HEADとみなさない。

**停止条件：** 本番のソースかバージョンを確認できない／`doPost` が重複／既存処理と候補が衝突／既存バックアップ未作成 → 本番編集をしない。

## 完了ゲート B：最小差分・監査準備

- 稼働コードを照合した後、必要なら不足した管理Ops処理だけを**同じApps Script**へ修正し、既存Webアプリの**同一デプロイを更新**する。本番URLを変えない。
- `emuzii_Web管理操作履歴` の10列見出し、`emuzii_ガチャ付与履歴` J列の `Web操作ID` の前後状態をバックアップ付きで確認。事前準備が必要なら承認済みの限定スキーマ変更だけとし、参加者・回数・当選履歴は変更しない。
- 本番管理者認証で `webAdminOpsRead` を一度だけ試みる。登録受付・ガチャ・簡易受付が正しい数と形式で返ること、管理操作の書き込みはまだ停止していることを確認。
- **先に `MIO_GACHA_ONSITE_RELEASE` を有効化しない。** 読取失敗なら本番解放を行わず、管理APIのエラー記録で原因を追う。

## 完了ゲート C：現場での最初の正規承認

- 読み取り、管理者認証、監査履歴保存先の最低条件が確認できた時点で、既存Vercelプロジェクトの現場用フラグだけを意図的にON。全体公開フラグとは独立。
- **架空顧客の本番登録・抽選・空付与はしない。** 最初に実際のお客様が来た際、管理者が本人・端末・メンシプ・残回数を照合し、その人だけチェックを入れて承認。
- 操作前の該当一人の権利・Web登録・監査履歴を確認。操作後に台帳とWeb反映を読み直し、**差分が一度だけ**、操作IDが一度だけ、他人のデータが無変更であることを確認。
- 通信切断時は**同じ操作ID**で状態確認し、新規IDで再実行しない。結果不明時は次の付与を止め、監査履歴と該当者を確認する。
- これが成功したら、他の来場者にも同じ個別対応を継続。全体機能公開の回帰結果は別件で追跡し、現場の個別承認を不要に遅延させない。

## 現場向け追加保護（2026-11-05 最終候補）

- **簡易受付の行番号だけでは確認操作できない**。管理APIは初回に読み取った受付日時（A列）・ColorSing名（B列）・簡易登録ブラウザID（C列）を必須にし、GASも台帳原本と照合。不一致なら監査記録を書かず停止。A列の日時書式が旧型のUTC文字列でも、読み取り時の原文をそのまま照合する。
- 管理APIがいったんGASに書き込んだ可能性があれば、再試行時の403（認証切れ）や503（解放停止）でも**最初の操作IDを削除しない**。認証・接続復旧後に同じIDを再確認する。初回の確定した事前拒否のみ再試行キューを破棄できる。
- 付与先は名前・MIO-IDが一致し、ガチャ台帳 F/H/O 列（総権利・残回数・特別付与）が空欄でない非負の整数で、残回数が総権利数以下のときだけ操作できる。重複IDや別人のガチャ行は**閲覧可・付与不可**で手動調査に回す。
- ここまでの重点テスト **71/71 PASS（GitHub Actions #42022206521）**。登録系全体回帰の別2系統は失敗が残り、現場GAS接続復旧の完了を意味しない。

## 保護するもの

**変更禁止**：本番URL、新規Apps Scriptプロジェクト、新規Webアプリデプロイ、既存ガチャ/皆勤/当選データの上書き、ユーザーの二重MIO-ID発行、メンシプの推測付与、全面`Code.gs`置換、秘密情報の公開。

**障害時の方針**：現場承認フラグをOFFに戻し、現行デプロイと監査ログから原因を確認。書き込み成功済みの回数・当選履歴を勝手に巻き戻さない。復旧確認が済むまで二重操作しない。
