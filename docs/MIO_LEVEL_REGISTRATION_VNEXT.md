## 本人が確定した体験

- みおが「名前・発行者・利用レベル・既存MIO-ID」を1画面で指定して、専用の使い切りIDを1つ発行する。
- 利用者は**名前と発行IDだけを手入力**。登録時にブラウザ側で端末鍵を生成し、サーバーが署名を検証してログイン状態を作る。管理者が毎回承認する必要はない。
- 発行者の記録は本人のアクセス権ではない。**みおのサーバー認証済み管理画面**が発行することが必要。
- 新規参加者はGAS正本のID発行サービスで参加者IDを確保してから発行。既存参加者は**元のMIO-IDのまま**登録を復旧。名前だけでIDを推定・横取りしない。同名者は確定したmaster_idで区別。
- 別端末で入り直す、ブラウザ保存データが消えた、機種変更した場合：みおが新IDを発行。**直前の未使用IDはすぐ失効**。旧端末のセッションは新端末で認証成功するまで保ち、成功時に新端末だけを有効化する。最大1台。
- 以前のガチャ当選・残回数・皆勤・応募履歴は元の参加者IDに紐付く。**新規ガチャ付与や履歴のコピーは行わない**。

## リリース判定

成功＝みおが端末1台で対象の名前とLvを登録 →本人が名前＋IDで本登録 →旧閲覧/皆勤/ガチャに元IDの正本でアクセス →機種変更で最新IDだけ有効 →他端末では使用不可 →履歴/残回数は変化ゼロ。
セッションが消えた場合、端末鍵が残っていれば再認証。ブラウザの保存データ全消去で鍵も失った場合はみおのID再発行。旧セッションの安全な失効を毎APIで確認してから一般化する。

公式基準：OWASP Authorization Cheat Sheet（deny by default、every request）、OWASP Session Management Cheat Sheet（server-side session invalidation）。

## 既存API接続監査｜実装前提を固定（2026-11-26）

### 現行経路の確認

- `api-checkin.js` と `api-gacha.js` は `bridge.js` の従来 `mio_session` Cookie を読み、GASへ `participantId=MIO-W-...` とトークンハッシュを渡す。
- 新しい復旧登録はNeon上の `master_id=MIO-...` と `__Host-mio_vnext_session` を使う。現行コードにはこのセッションを従来GASセッションへ安全に引き渡す共通アダプターがない。
- したがって復旧登録が成功しても、現時点で従来の皆勤・ガチャへの権限連携が完了したとは扱わない。既存APIは未変更のまま保護する。

### 実装する接続境界

1. サーバー共通認証ヘルパーが、Cookieから新セッションを取得し、pepperでハッシュ化した値をDBの有効セッションと照合する。アカウント状態・セッション期限・世代・端末署名をリクエストごとに確認し、無効時は拒否する。
2. 権限は機能単位でサーバー判定する。皆勤と歌推しギャラリーはLv.2以上、メンシプガチャとメンシプギャラリーは有効期限内のLv.3だけを許可する。クライアントが送るMIO-ID・レベル・署名済み申告を認証根拠にしない。
3. 認証済みの `master_id` は、サーバー間GASブリッジの専用アクションで正本の参加者行へ一意に解決する。既存GASの `MIO-W-...` と `MIO-...` を同一形式として扱わない。曖昧一致・複数行・名前だけの一致は拒否する。
4. 既存の従来ログインは、対応するレベルアカウントへ安全に移行済みと確認できるまで利用可能な状態を保つ。復旧登録の成功時だけ、そのMIO-IDに対応する旧端末セッションを切り替える。別利用者の発行・再発行は影響させない。
5. ガチャ抽選・履歴・残回数は従来GAS処理を唯一の正本とする。権限アダプターは認証・認可だけを担当し、抽選を再実行したり履歴/残回数を複製・更新したりしない。
6. ギャラリーはAPIと配信物の両方を監査する。既存の公開カタログ・公開静的URLを認証済みと見なさず、限定画像・動画の実ファイル経路にアクセス制御がない場合は、その素材を公開せず機能を未接続のままにする。
7. 旧セッション経路を止める変更は、皆勤・ガチャ・全ギャラリー入口・特殊復旧（PR #100）を横断する統合試験が完了し、本人が本番変更を承認するまで行わない。

### 次の実装単位と受入条件

- 第一段階は本番GASを変更せず、PR内に共通レベルセッション検証モジュールと単体試験を追加する。テストは、期限切れ・世代更新・署名欠落・レベル不足・改ざんMIO-IDをすべて拒否し、公開機能だけをログイン不要にする。
- 第二段階はGASソースと現行本番版の一致を読み取りで確認し、MIO-IDから既存参加者IDへ一意に解決する読み取り専用境界を設計する。現行版と一致しない限り、既存GASへの変更を適用しない。
- 第三段階で対象APIを一つずつ隔離Previewへ接続する。皆勤は読み取り・チェックイン、ガチャはカタログ・履歴・抽選を別々に確認し、抽選履歴と残回数が基準値から意図せず変わらないことを検証する。
- 全入口を通した統合試験とiPhone/Android実機確認が未合格の間は、Lv.2/Lv.3の利用可能表示・本番リリース設定を有効にしない。
