# MIO運営管理センター — 運用・障害設計（2026-10-31）

## 事実と不明点
- 現行`bridge.js`のApps Script接続には20秒タイムアウトがある。10/30のガチャ結果非表示が20秒制限/回線/アクセス集中によるものかは未確認。
- `api-gacha.js`は401（認証なし）と409（多くの下流例外）を返すため、409だけでは確定済み抽選と未確定抽選を区別できない。
- `gacha-page.js`はdrawIdを端末に保存し、読み取り系のみ再試行。抽選再送は抑止され、履歴照合後に同じdrawIdで再開する。二重消費防止の思想は維持する。
- 10/30のVercel実行ログに出ていたSSL/URL解析警告は抽選結果消失の直接証拠ではない。
- 本PRは管理の**承認待ち通知30秒**まで。ガチャ障害の自動チケットは後続実装。

## 採用方式の比較
| 候補 | 長所 | 課題 | 判断 |
|---|---|---|---|
| 管理者ブラウザ→既存GASを直接ポーリング | 追加費用最小 | GAS呼び出し増、処理待ち、管理画面離脱で停止 | 小規模の暫定手段 |
| Vercelの集約API→同一イベント台帳をポーリング | 独立した読取・通知、操作履歴を監査しやすい | 集約台帳・認証設計が必要 | 次期基盤の第一候補 |
| WebSocket/リアルタイム配信サービス | ほぼ即時 | 常時接続・追加費用・運用複雑化 | 実負荷を計測後に選択 |
| GAS時間主導で通知を集約 | GAS内で完結 | 即時性が低く、障害時にGAS自体が遅くなる | 予備または定期チェック |

本番は既存Vercel・GAS・Google管理台帳を維持する。参加者の権利・当選履歴の正本を新DBへ移行しない。集約台帳を作る場合でも**障害チケットと監査履歴だけ**を保持する。

## 障害分類と管理者の最初の1操作
| コード | 現象 | 管理画面に表示する一次対応 |
|---|---|---|
| AUTH_COOKIE_MISSING | 現在のブラウザに署名済みCookieがない | 登録済み端末・Web参加IDの照合と復旧候補を表示 |
| AUTH_DEVICE_MISMATCH | 旧端末・別ブラウザ扱い | 正本IDを確認し、指定端末だけ臨時許可 |
| REG_PENDING | Web登録が未承認 | 対象MIO-ID・メンシプ状況を表示し承認操作 |
| REG_DUPLICATE | 同名/複数Web IDが存在 | 既存の正本IDに接続。新規IDの自動発行は禁止 |
| GAS_TIMEOUT | GAS応答が規定時間を超えた | 直前の操作IDを照合。新しい操作IDは作らない |
| DRAW_REPLY_LOST | 抽選確定後のHTTP応答が表示に届かない可能性 | 同じdrawIdの確定履歴から結果を再表示 |
| DRAW_UNKNOWN | 抽選の確定有無が不明 | 管理者がGAS履歴・残権利を照合、無条件の再抽選禁止 |
| DRAW_HISTORY_CONFLICT | 1drawIdが複数行/内容不一致 | 自動処理を止め、監査台帳で正本を確認 |
| GRANT_UNCERTAIN | 回数付与の応答不明 | 元のoperationIdで再確認（新規付与禁止） |

## 管理画面のチケット台帳（次フェーズ）
必須の非公開フィールド：
- `incident_id`（ランダム・不変）、`site`、`occurred_at`、`category`、`severity`
- `participant_id`または管理台帳の照合可能な限定参照（名前だけの紐付けは不可）
- `draw_id`または`operation_id`（存在する場合のみ）
- `state`：`unhandled` → `working` → `resolved`（再発は新チケット）
- `operator_id`、`action`、`performed_at`、`before/after`、`resolution_note`
- `request_id`とサーバー処理段階（認証、GAS呼び出し、抽選確定、HTTP返信、画面描画）
- **保存禁止**：原Cookie、管理者コード、トークン、資格情報、住所、IP全文、当選景品画像の生データ

チケットの作成は「当該操作のサーバー観測」と「認証済み参加者の限定通知」で行い、なりすましで他人のチケットを作れないよう署名・レート制御する。GAS側の確定履歴を唯一の権利正本とする。

## ワンクリック復旧のルール
- 管理者コード/パスキー認証後、対象者と復旧処理が一致すれば1操作で実行可能にする。
- 管理者による業務ルールの一時変更は許可するが、対象者・対象操作・期限・理由の範囲で記録し、他ユーザーのデータには波及させない。
- **抽選の既存結果を表示**する操作は既存当選履歴の読取のみで実行し、回数を減らさない。
- **回数の再付与**は確定履歴を確認して不足を証明できた場合のみ、同一operationId・監査付きで実行。
- ガチャ結果未確定の場合、再送も同じdrawIdで実行。通信断でも独立した新抽選を開始しない。
- UI上の「対応中」「解決」は作業チケットの状態であって、ガチャ権利や承認状態ではない。

## Phase 2C：管理者1操作の端末・ログイン復旧（2026-10-31、開発版のみ）

### 採用した方法
- 登録済みブラウザの**署名付き`mio_light_session`**からのみ復旧申請可能。ユーザーが自由な名前、他人のWeb ID、MIO-IDを渡して権利を取得できない。
- サーバーでNeon `statusV201`（同一トークンハッシュ、承認済み、重複確認済み、既存MIO-ID照合済み）とGAS `status`（同一Web ID、正しい登録名、承認済み、既存ガチャ確認済み）を**別々に検証**する。どちらかが不明なら申請不可。
- 専用表`mio_device_recovery_requests`は**同じ既存Neon登録DB**に追加するマイグレーション案（**未適用**）。元のID・ログイン・参加者・皆勤・ガチャ・景品は更新しない。
- 申請に保存するのは正規Web ID、正規MIO-ID、表示名、HMACで拘束したブラウザトークンの非可逆値、状態、管理者承認方式、時刻。**原Cookie・原token・管理者コードを保存しない**。
- 申請から15分で失効。管理者コード/Face IDによって一覧を閲覧し、本人照合済みの1件に対して**1操作で許可**。承認時は同一operationId再送保護。承認済みでも新しい端末の署名なし認証は不可。
- 元のブラウザに戻った本人が`claim`を押すと、**NeonとGASの照合をもう一度実施**し、同じブラウザの署名・トークン拘束が一致する場合だけ、従来の`mio_session`を再発行する。抽選・付与・新規参加者登録は行わない。
- 既存セッションの返信が通信断で届かなかった場合だけ、同じブラウザ署名を持つ利用者が2分以内に再試行可能。それ以外は新しい管理者承認が必要。
- 署名付きの簡易Cookieすらないブラウザ・未確認の重複登録・GAS/Neonの不一致は、**自動復旧しない**。この場合の安全な本人確認と端末再紐付けは別途設計。
