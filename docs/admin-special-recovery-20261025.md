# 管理者特例復旧 — 本番反映前チェック (2026-10-25)

対象: まーくん MIO-0010 / サスケ MIO-0018。管理者による本人確認済み。本人との連絡は現在不可。

## 既存実装を確認した結果
- `Code.gs` の通常登録は新規Web-ID/トークンとログインIDを扱う。単なるシートの承認欄変更では、新端末の署名済みセッションCookieを発行できない。
- `BrowserAddV189Patch.gs` の `approveAdditionalBrowserV189Patch_` は既存Web登録行が存在すること、H/K/P/Lの整合、参加者名一致を要求する。新端末の未登録Web-IDを作る機能ではない。
- `api-register.js` は `MIO_REGISTRATION_RELEASE` により本番登録を停止できる。
- このブランチの `api-recovery.js` は `MIO_RECOVERY_RELEASE` で停止しており、GAS `recover` アクションの実装・本番デプロイ・E2E検証がない。

## 最小実装の要件
1. GAS側で管理者が対象MIO-IDをホワイトリスト指定してランダムな一回限りの復旧コードを発行する。コードそのものは保存せずSHA-256のみ保存し、有効期限を設定。管理者承認の証跡を残す。
2. 利用者が後日新端末で復旧コードを入力。サーバーが新Web-IDとトークンを生成し、GASがロック内で未使用コードと対象MIO-IDを照合して、新Web登録行を承認済みで作成。旧行は変更しない。
3. GASからWeb-ID、MIO-ID、トークンハッシュを含む確定結果を返し、Vercelが検証後に署名済みHttpOnly Cookieを設定する。リトライで二重登録しない冪等性を確保する。
4. 承認された新Web行は `status` で検証できること。既存の名前厳密一致チェックが別名表記の「まーくん」を拒否しないよう、MIO-IDに紐づく管理者承認済みエイリアスを限定的に許容する。
5. 全員共通の登録制限を緩めない。ガチャ・皆勤・FA・旧端末・既存登録行・本番URLを変更しない。
6. テスト: 未承認MIO-ID拒否、期限切れ/再利用拒否、他者コード拒否、二重送信、旧端末維持、2名の新端末status承認。合格後のみ本番反映。
