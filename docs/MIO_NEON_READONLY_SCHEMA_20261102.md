# 翠央1周年｜Neon接続先の読み取り専用スキーマ目録（2026-11-02）

## 目的と限界

既存の管理センター障害記録を検討する前に、**接続済みNeon**で見えるデータベースのテーブル一覧だけを確認した。プロジェクトの一覧、ブランチ、データベース名、テーブル名のメタデータを確認し、**SELECTによる実データ行の取得、DDL/DML、ブランチ作成、マイグレーション、環境変数変更は行っていない**。

この接続先が既存Vercelの本番環境変数に設定された**正本DBであることは未証明**。名前に「mio」が含まれることだけで本番DBと確定しない。

## 確認できた構造（接続済みNeonプロジェクト）

接続上で確認したプロジェクトは `neon-byzantine-chair`。ブランチ `main`（Neonのデフォルト）と `mio-reg-v2-isolated-test-20261019` をそれぞれデータベース `neondb` のメタデータだけで確認した。

| 対象 | 確認できたテーブル名 |
|---|---|
| Neon `main` | `mio_ip_audit_v202`, `mio_name_registry_v201`, `mio_name_review_v201`, `mio_registration_v2` |
| Neon `mio-reg-v2-isolated-test-20261019` | `mio_registration_v2` |

どちらのブランチのテーブル一覧にも、開発版の障害管理SQLが想定する **`mio_admin_incidents` / `mio_admin_incident_audit` は見当たらない**。そのため、Draftの障害センターコードを**本番につなぐ準備はできていない**。

## 絶対に解除しない停止ゲート

1. 実際に使用中のVercel/GAS側から**接続先の識別情報だけ**を非公開で照合し、Neonの接続先を正本と確定する。環境変数の秘密値・パスワードをIssueやログに転記しない。
2. 正本DBで既存参加者・登録・抽選・当選・皆勤がどこに存在するかを確認する。既存のスプレッドシート/GASとの責務境界を明確にする。
3. 本番既存データのバックアップと復元手順、監査テーブルの権限/スキーマ、同時実行時の安全性を別工程でレビューする。
4. `db/mio-admin-incidents-20261031.sql` は**設計候補のみ**とし、正本確定・バックアップ・オーナー承認までは**一切実行しない**。
5. `MIO_INCIDENT_CENTER_RELEASE`、`MIO_INCIDENT_RECORD_RELEASE`、`MIO_INCIDENT_WRITE_RELEASE` はOFFのまま。新規管理APIルートも追加しない。
6. Issue #66の稼働GASソース/デプロイ/バックアップ照合、既存操作監査タブ/付与履歴J列の未整備、実機、参加者データ保護の停止条件も継続する。

**結論：関連名称のテーブルが見つかったことは構造確認の前進だが、本番正本DBの確認でも書込/公開許可でもない。PR #76はDraftを継続し、main、Vercel Production、GAS、Sheet、Neonのいずれにも変更しない。**
